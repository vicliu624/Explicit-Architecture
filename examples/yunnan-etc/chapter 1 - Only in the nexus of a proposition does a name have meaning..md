# 第 1 章
## 我们究竟以为自己在做什么工程

**章首引句**

只有命题才有意义；名称只有在命题的语境中才有意义。

**本章的核心问题**

这一章不要求你立刻接受某种完整方法。  
它只要求你先停下来想三个问题：

- 我们项目中最常用的那些词，真的是已经有意义的对象，还是只是一些被习惯性使用的名字？
- 这些名字到底只有在什么命题里才成立？是谁在什么条件下判定它成立？
- 我们平时以为自己在“描述对象”，还是实际上一直在“组织让名称获得意义的事实结构”？

如果这三个问题没有被认真问过，那么后面的建模、分层和实现，往往只是建立在一批尚未真正获得意义的名称之上。

**这一章真正要打碎的旧信念**

软件工程面对的是一组天然给定的对象，我们只是把它们正确搬进系统。

**这一章真正要建立的新观念**

名称本身没有现成的工程意义。  
对象不是先天地给定的，而是名称在某种命题结构、事实结构和判定结构中获得意义之后，才被组织出来的。  
软件工程首先面对的，不是对象清单，而是让名称成立的命题关系。

**章节说明**

在大多数软件工程讨论里，我们几乎总是从名词开始。  
我们谈用户、订单、账户、任务、审批、状态、完成，  
仿佛这些词天然就指向某些稳定存在的对象。  
于是，工程师很容易形成一种非常强、也非常习惯的感觉：

- 世界里本来就有这些对象
- 我们只是在把它们搬进系统
- 名词既然已经在那里，建模只是把它们整理出来

但这一章要打碎的，恰恰就是这种感觉。

因为一个名称本身并不先天地有意义。  
“用户”这个词本身没有工程意义；  
“订单”这个词本身也没有工程意义；  
“完成”这个词本身同样没有工程意义。  
一个名称只有被放进某种有结构的命题关联里，  
它才真正开始在系统中“成其为”某个对象、某个状态、某个判断。

换成更工程化的话说，就是：

- 不是先有“用户”，再有系统
- 而是先有“谁在什么条件下被算作某类用户”的判定结构

- 不是先有“订单”，再有流程
- 而是先有“什么事实被组织成一次可追踪、可结算、可撤销的业务单元”的组织方式

- 不是先有“完成”，再有状态
- 而是先有“谁基于什么证据宣布某事完成，并因此放开哪些后续动作”的制度关系

这就是为什么这一章的起点，  
不应该只是“世界不是对象堆”，  
而应该更直接地落在这件事上：

很多团队以为自己已经在处理对象，  
其实他们手里往往还只有名字，  
还没有意义。

这件事在当前工程里看得非常清楚。

这个仓库表面上充满了熟悉的对象名词：操作员、白名单、订单、审核、撤单、完成、业务流水。  
看上去，它像一个对象齐全、流程明确的系统，工程师只需要给这些对象建表、建类、写接口，再让它们沿着流程移动。

可是一旦进入实现，就会发现这些词并不是天然清楚的对象。  
它们真正的意义，总是来自它们被放进了什么样的命题结构。

比如，“操作员”这个词，表面上像一个稳定对象。  
但在这个工程的“操作员申请 / 审核”实现里，它真正对应的并不是一个天然对象，而是一串被压缩过的命题：

- 某人正在申请被纳入某种授权结构
- 这次申请发生在某个组织边界内
- 它涉及角色、渠道、启用状态、预付费权限等一组变更
- 某个审核者会基于这些变更作出通过或不通过的判定

可系统当前并没有把这些命题显式表达出来。  
在 `TblOperatorModifyApply` 里，我们首先看到的是一条记录，里面保存了 `oldOrg`、`oldRoleIds`、`oldOrderChannels`、`reviewStatus` 这类字段；在 `OperatorApplyServiceImpl` 里，`generateCreateApply` 和 `generateModifyApply` 负责把这些值拼成一条申请快照；审核通过后，`operatorApplyReview` 再调用 `createWhiteList` 或 `updateWhiteList`，把这条记录拷贝进白名单并重写 `TblRelationUser` 关系。

这说明系统是怎么让“操作员”获得意义的？  
不是靠“操作员”这个名字本身，  
而是靠一整套隐含的命题结构。  
只是这套结构今天大多被压扁成了对象字段和状态切换。

“订单”“审核通过”“完成”也是一样。  
它们看起来像现成对象或现成状态，  
实际上却只有在某些命题里才成立。

在 `OrderAuditController.saveOrderAudit()` 里，只要系统发现订单当前处于“审核中”，就会把订单状态改成“已撤单”或“已拒绝”，然后更新撤单记录；  
在 `TblEtcBusinessSeq` 里，“办理中 / 办理成功 / 取消办理”和 `businessCompleteTime` 被直接做成字段；  
在 `ThirdOrderServiceImpl` 的撤单流程里，代码会直接 `setStatus(2)`，如果 `businessCompleteTime` 为空就补一个当前时间。

这背后的问题不是“状态字段多不多”，  
而是：

- “完成”这个名称真正对应的命题没有被显式写出来
- “审核通过”真正成立的条件没有被显式写出来
- “撤单成功”真正意味着哪些事实改变没有被显式写出来

于是，系统最后呈现出来的，就不是“命题结构”，  
而是“名称先被当成对象，再被压成状态值”。

也正因为如此，这一章真正要帮助听众看见的，不只是：

- 世界不是一堆对象

而是更尖锐的一步：

- 名称本身并不自动指向对象
- 对象只有在某种命题结构里才获得意义
- 软件工程首先做的，不是搬运对象，而是组织让名称成立的命题

一旦这点被看见，后面的很多问题才会真正变得可理解。  
为什么团队明明都在说同一个词，却常常说的不是同一件事；  
为什么模型会迅速老化；  
为什么状态越来越多，系统却越来越难解释；  
为什么很多设计争论表面上像对象之争，实际上却是命题结构之争。

换句话说，  
第一章真正要让听众第一次意识到的是：

你以为自己已经在处理对象，  
其实你可能还只是在处理名字。  
而如果名字还没有被放进清楚的命题语境中，  
那么对象其实根本还没有被建立起来。

**需要提升的能力**

这一章希望读者提升的，不是多记住几个术语，  
而是从“看到名字”上升到“看到名字如何获得意义”的能力。

更具体地说，需要提升的是下面几种能力：

- 识别空名词的能力：能够意识到“用户”“订单”“完成”这类高频词并不自动有意义，它们可能只是被习惯性重复的名字。
- 补出命题结构的能力：能够把一个孤立名词补成一句完整判断，例如“谁在什么条件下被算作什么”，而不是只停在名称层。
- 识别成立条件的能力：能够说清一个词要在什么条件下才成立，而不是只知道它对应哪张表、哪个字段、哪种状态。
- 识别判定者的能力：能够分辨是谁、依据什么规则、有权把某个名称放进一个成立的命题里。
- 识别绑定事实的能力：能够看见一个名称一旦成立，会同时绑定哪些后续事实、权限变化、责任转移和系统动作。
- 识别反例与失效的能力：能够主动发现哪些异常、回滚、挂起、补录会让一个看似稳定的名称失去原本的意义。

**能力训练建议**

这一章不适合用“背术语定义”或者“统一名词表”的方式来训练。  
更适合的做法，是训练大家把熟悉的名词重新放回命题里。

更具体一点，我会建议这样练：

- 先从自己项目里挑出三个最高频、最理所当然的词，不要挑太生僻的词，因为越熟悉的词越容易遮蔽判断。
- 第一步禁止回答“它是什么”，先回答“它只有在什么句子里才成立”，强迫自己把名词补成命题。
- 第二步明确写出“谁有权判定它成立”，借此暴露组织边界、职责边界和规则来源。
- 第三步继续追问“它一旦成立，会联动哪些后续事实”，训练自己看见名字背后被压缩的制度后果。
- 第四步补上“哪些例外会动摇它的成立”，把那些平时被状态码掩盖的异常、回滚、挂起和补录重新看见。

如果要结合这个工程现场练习，我建议直接拿下面三个词：

- 操作员
- 审核通过
- 完成

这样选的原因很直接：

- “操作员”适合训练大家看见名字背后的授权命题，而不是把它只看成一个用户对象。
- “审核通过”适合训练大家看见判定结构，而不是只看一个 `reviewStatus`。
- “完成”适合训练大家看见成立句式，因为它最容易在系统里被压扁成一个最终状态值。

我的具体建议是，不要把这项练习做成“术语解释题”，  
而要把它做成“命题补全题”。  
练习结束后，团队至少应该能意识到：

- 他们平时使用的很多词，其实只是名字
- 这些名字只有进入某种命题结构时才获得意义
- 一旦命题结构没有被显化，所谓“对象”往往只是伪装得很稳定的空名词

**在当前工程里，旧信念最明显的两处体现**

**第一处：把名称直接当成对象，从而跳过了它赖以成立的命题结构。**  
这个工程里大量领域类都是 `TblXxx` 形式，建模起点明显偏向“先有表，再生成对象”。  
这会让团队很自然地觉得：  
现实世界已经天然分好类了，工程师只需要把这些名字对应成类、把字段对应成属性即可。

在“操作员申请 / 审核”这条实现里，这种旧信念表现得尤其典型。  
`TblOperatorModifyApply` 直接把申请建模成一条记录，里面保存的是 `oldOrg`、`oldRoleIds`、`oldOrderChannels`、`reviewStatus` 这种字段快照；随后，`OperatorApplyServiceImpl` 里的 `generateCreateApply` / `generateModifyApply` 负责拼出这条快照；审核通过后，`operatorApplyReview` 再调用 `createWhiteList` / `updateWhiteList`，把它拷贝进白名单并重写 `TblRelationUser` 关系表。

这背后的默认假设是：  
“操作员”这个名字已经天然指向了一个对象，我们只是在更新它的属性。

但如果按新的第一章判断来看，真正该先被建立的并不是对象，  
而是让“操作员”这个名字获得意义的命题：

- 某人在申请进入怎样的授权结构
- 谁在审核这次授权
- 这次授权发生在哪个组织边界里
- 它授予了哪些渠道、角色、范围和限制
- 这些授权从什么时候起生效，到什么时候失效

现在，这些命题大多没有被显式表达出来，  
而是被压扁成字段复制、对象覆盖和状态更新。  
也就是说，系统太快地从“名字”跳到了“对象”，  
却没有把名字真正获得意义的中间结构建立出来。

**第二处：把名字当成状态标签，而不是把它放回成立它的命题。**  
在订单审核、撤单、文档修复、业务完成这些流程里，代码经常通过修改 `status`、`reviewStatus`、`businessCompleteTime` 来表达“审核通过”“已撤单”“已完成”。  
这背后的默认理解是：  
一个名称一旦需要成立，只要把某个对象字段改成某个值就可以了。

在“订单审核 / 完成”这条实现里，这种写法非常直接。  
`OrderAuditController.saveOrderAudit()` 只要发现订单当前处于审核中，就把订单状态改成“已撤单”或“已拒绝”，然后更新撤单记录；`TblEtcBusinessSeq` 又把“办理中 / 办理成功 / 取消办理”和“业务完成时间”直接做成字段；更典型的是 `ThirdOrderServiceImpl` 的撤单流程里，代码直接 `setStatus(2)`，如果 `businessCompleteTime` 为空就补一个当前时间。类似的习惯也出现在 `TblUserDocumentFix` 这类流程对象里，`status` 被定义成“待用户填写 / 待审核 / 待人工填写 / 完成”。

但如果按这一章的引句来理解，问题就会变得很清楚：

- “完成”这个名字本身并没有意义
- 它只有在某个命题里才有意义

例如：

- 某个流程节点已经被谁正式判定结束
- 判定它结束所需的资料、审核、外部状态是否已经齐备
- 一旦判定结束，哪些动作因此被允许，例如打印或发送回执单
- 哪些例外会让这个“完成”被推翻、挂起或补录

现在这些真正让“完成”获得意义的命题，大多散落在控制器、服务和异常补丁里，  
最终却只汇总成一次“改状态”或者“补时间”。  
于是系统没有显式表达“完成是在什么命题中成立”，  
而只是把“完成”当成某个字段最终可以写成的名字。

如果把这一章讲透，听众最后应该能意识到一件事：  
我们平时以为自己在做的是“对象建模”，  
其实很多时候，我们连对象都还没有真正建立起来。  
我们手里先拿到的，往往只是名字。  
而软件工程真正困难、也真正关键的地方，  
就在于能不能把这些名字放进清楚的命题语境里，  
让它们真正获得意义。
