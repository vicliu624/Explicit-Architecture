# 第 3 章
## 为什么反映式工程会失效

**章首引句**

我的语言的界限，意味着我的世界的界限。

**章节说明**

到了这一章，我们要把前两章的判断再往前推进一步。

如果世界并不是天然对象的总和，而是被组织起来的事实结构；  
如果建模也不是被动反映现实，而是主动构造关于事实的图像；  
那么一个更尖锐的问题就会出现：

为什么传统的反映式工程，在现代业务系统里会不断失效？

很多团队遇到项目失控、模型老化、状态混乱、跨团队争议反复出现时，第一反应通常都是从执行层面解释问题。  
他们会说，是设计不够好、实现不够稳、测试不够严、协作不够细、责任不够到位。  
这些判断当然有时成立，但它们并没有触到更深的一层。

反映式工程之所以会失效，很多时候并不是因为团队不够努力，  
而是因为它默认面对的是一套静态、清晰、可复制的对象世界。  
可现代业务系统真正面对的，往往不是“静态对象”，而是“人、组织与世界语义”不断互动的系统。

这类系统的核心困难，往往不是“如何把东西算对”，  
而是“如何把事情说清楚”。  
它们首先是解释问题，其次才是计算问题；  
首先是赋义问题，其次才是实现问题；  
首先是语言边界问题，其次才是接口边界问题。

也正因为如此，很多看上去像“技术失效”的地方，本质上其实是解释失效。

一个名词可能在不同角色那里指向不同东西。  
一个状态可能在不同流程里意味着不同后果。  
一个字段可能看起来叫同一个名字，但承载的其实不是同一类事实。  
一旦这些地方没有被稳定下来，工程师就会不断遇到一种熟悉的局面：

- 代码已经写了，但大家说的不是同一件事
- 状态已经流转了，但谁也说不清它到底意味着什么
- 数据已经落库了，但不同模块拿它当成不同东西来用
- 问题已经修了，但争议还会以另一种形式回来

这就是为什么反映式工程在业务系统里会越来越吃力。  
它擅长处理“对象复制”问题，却不擅长处理“语义持续变动”问题。  
它擅长假定世界已经被分好类，却不擅长面对这些类别本身仍在漂移。  
于是，团队越努力地去维持一个已经失稳的语言系统，就越容易把问题表现成：

- 更多状态
- 更多补丁
- 更多校验
- 更多修复任务
- 更多同步逻辑
- 更多“例外中的例外”

在这个工程里，这种失效并不是抽象判断，而是已经写进了很多具体实现。

比如，“申请”和“订单”的边界并不稳定。  
在 `TblObuTakeOrderInfo` 里，字段名是 `applyId`，注释却写着“订单号”；  
在 `TblStockUsedReturnInfoMapper` 里，方法参数叫 `applyId`，SQL 却拿它去匹配 `order_id`；  
在 `UnSignExpandInfoRequest` 里，同一个 `applyId` 又会随着 `status` 的不同，分别表示“签约的 applyId”或“拓展推送的 applyId”。  
这说明失效并不只是“某个字段写错了”，而是同一个术语边界本身没有稳住。

再比如，“审核通过”“成功”“完成”这些状态词并不稳定。  
`TblWxOrderInfo.confirmStatus` 里的审核状态是“0-待审核 1-成功 2-失败”；  
`TblOperatorModifyApply.reviewStatus` 里的审核状态是“0-待审核 1-通过 2-不通过”；  
`TblPrepaidCancelInfo.fundStatus` 里又变成“0 未计算，1-已计算未审核，2-审核通过，3-审核不通过，4-退款成功，5-挂起”；  
而 `TblEtcBusinessSeq.status` 则表示“办理中 / 办理成功 / 取消办理”。  
这意味着团队嘴里看似相同的词，在代码里并不是同一种事实结构。  
一旦有人说“这个已经审核通过了”或“这个已经完成了”，真正的问题就不只是程序有没有执行完，而是大家是否在用同一种语言。

还有一个更强的信号是：系统里出现了大量用来“补救解释失稳”的任务。  
`OrderVerifyTask` 会定时校验“未获取到车辆信息或账户信息的订单”；  
`RepairCardHistoryTask` 在发现“不存在 businessSeq”时，会“补一个订单，并补一个 seq 记录”；  
甚至还专门存在 `TblOrderStatusRefresh` 这样的状态刷新结构。  
这些实现说明，系统并不只是在修 Bug，它也在持续修补那些没有被稳定表达好的事实关系。

因此，这一章的目的，就是帮助我们把一种很常见的误判纠正过来：

项目失控、模型漂移、状态混乱，不一定首先是执行不力。  
很多时候，真正先失效的，是团队用来组织世界的语言本身。

一旦这点被看见，我们才有可能重新区分：

- 哪些问题真的是实现问题
- 哪些问题其实是语言边界问题
- 哪些问题是赋义不稳问题

**本章的核心问题**

这一章希望你先学会停下来问三件事：

- 这个问题真的是某个实现写得不对，还是我们根本没有稳定地定义术语边界？
- 这里失败的是一次执行，还是同一个状态在不同上下文里已经发生了含义漂移？
- 我们现在修的是一个 Bug，还是在用补丁维持一套已经开始失稳的语言系统？

如果这三个问题没有被认真区分，那么团队就很容易把“语言问题”持续当成“执行问题”来修。

**这一章真正要打碎的旧信念**

项目失控主要是执行不力、设计不好、实现不稳。

**这一章真正要建立的新观念**

现代业务系统中的很多失效，首先不是计算失效，而是解释失效。  
一个系统真正能稳定运行，不只取决于代码是否执行正确，也取决于它是否稳定地划定了术语边界、状态含义和角色之间的赋义关系。

**需要提升的能力**

这一章希望读者提升的，不只是排查 Bug 的能力，而是更深一层的失效辨识能力：

- 区分实现问题与语言问题的能力：能够判断一个故障到底是代码没写对，还是术语本身没说清。
- 识别语言边界的能力：能够发现哪些名词看似稳定，实际上在不同模块、角色或流程里指向了不同东西。
- 识别赋义漂移的能力：能够看出同一个状态词在不同上下文里承载了不同事实，因此不能被简单地当成同一种“成功”或“完成”。
- 从补丁中反推结构问题的能力：能够把 `Repair`、`Verify`、状态刷新、补录、补单这类实现，看成语义结构失稳的信号，而不只是偶发技术债。
- 从故障回溯解释系统的能力：能够顺着一次事故往回追，找到真正失效的是哪个词、哪个边界、哪种赋义关系。

**能力训练建议**

这一章最适合训练的，不是“怎么更快定位异常日志”，  
而是“如何把一次故障重新翻译成语言和赋义问题”。

更具体一点，我会建议这样练：

- 拿一个团队熟悉的事故、返工点，或者反复争议的流程，不要挑太偶发的问题，越反复出现越适合练。
- 先禁止大家直接下“谁没处理好”“哪段代码不稳”“哪个接口有问题”这类结论，先把 blame 语言暂停下来。
- 先写出这次问题里最关键的三个词，例如“申请”“审核通过”“完成”“同步成功”“订单状态”。
- 然后逐个判断：哪个术语的边界不清，哪个状态的含义漂移了，哪个名词被不同角色用成了不同东西。
- 最后再区分：这次问题的主因到底更像实现问题、语言边界问题，还是赋义不稳问题；如果三者都有，哪一个是上游原因，哪一个只是表层症状。

如果要结合这个工程现场来练，我会建议直接从下面几组材料入手：

- `applyId` / `orderId`：看“申请”和“订单”在不同模块里到底是不是同一种东西。
- `reviewStatus` / `confirmStatus` / `fundStatus` / `status`：看“审核通过”“成功”“完成”这些词到底是不是同一种结果。
- `OrderVerifyTask` / `RepairCardHistoryTask` / `TblOrderStatusRefresh`：看系统是在修一次实现错误，还是在持续修补一套不稳定的解释结构。

我的具体建议是，不要把这项练习做成“事故复盘里的责任判断题”，  
而要把它做成“失效类型识别题”。  
练习结束后，团队至少应该能更清楚地说出：

- 这里坏掉的是实现
- 这里坏掉的是术语边界
- 这里坏掉的是状态赋义

只有做到这一步，后面的修复才不会一直停留在补丁层。

**在当前工程里，反映式工程失效最明显的三处体现**

**第一处：名词边界没有稳住，`applyId` 和 `orderId` 被交叉使用。**  
在 `TblObuTakeOrderInfo` 里，主键字段名叫 `applyId`，注释却写的是“订单号”。  
在 `TblStockUsedReturnInfoMapper` 里，`getBondStatus(@Param("applyId") String applyId)` 这类方法，又直接拿 `applyId` 去查询 `tbl_obu_issue_order_info` 表里的 `order_id`。  
而在 `UnSignExpandInfoRequest` 里，同一个 `applyId` 甚至会因为 `status` 不同，分别指代“签约的 applyId”或“拓展推送的 applyId”。

这说明问题并不是简单的命名不统一。  
更深的问题是：团队并没有稳定回答“申请”和“订单”到底是不是同一种业务单位。  
一旦这个边界本身不稳，后面的映射、查询、同步和追责都会不断滑动。

**第二处：状态词稳定不了，`审核通过`、`成功`、`完成` 在不同流程里不是同一种事实。**  
`TblWxOrderInfo.confirmStatus` 的“审核状态”是“待审核 / 成功 / 失败”；  
`TblOperatorModifyApply.reviewStatus` 的“审核状态”是“待审核 / 通过 / 不通过”；  
`TblPrepaidCancelInfo.fundStatus` 里又把“审核通过”嵌在“已计算未审核 / 审核通过 / 审核不通过 / 退款成功 / 挂起”这样一条完全不同的状态链里；  
而 `TblEtcBusinessSeq.status` 则把“办理成功”当成另一种维度的结果。

这意味着，看似熟悉的状态词，其实并没有构成统一语言。  
团队表面上都在说“审核通过”“成功”“完成”，但代码里的这些词并不共享同一组后续事实。  
因此，很多争议并不是“某个状态没改对”，而是“大家拿着同一个词，说的却不是同一个世界”。

**第三处：系统不得不依赖 `Repair`、`Verify`、刷新任务来维持解释的一致性。**  
`OrderVerifyTask` 的职责是“定时校验未获取到车辆信息或账户信息的订单”；  
`RepairCardHistoryTask` 在注释里直接写着“如果不存在 businessSeq，就补一个订单，并补一个 seq 记录”；  
`TblOrderStatusRefresh` 这样的结构，则进一步说明系统需要专门维护“状态刷新”这件事。

这些实现当然有现实价值，但它们也暴露出一个事实：  
系统面对的已经不只是偶发实现错误，而是多种事实图像之间持续失配。  
当订单、业务流水、历史记录、账户信息、车辆信息之间的解释关系不稳定时，系统只能靠一层又一层校验、补录、刷新和修复任务来维持表面一致。

换句话说，这里真正失效的，不只是某条流程，  
而是团队用来描述流程的语言已经无法稳定覆盖现实变化。

如果把这一章讲透，读者最后应该能意识到一件事：  
很多项目之所以越来越难做，  
并不是因为团队越来越不会写代码，  
而是因为他们还在用处理静态对象的方法，  
去处理一个本质上不断发生赋义、漂移和重解释的世界。
